## 应先做的四项

| 优先级 | 技术/调整位置 | 要解决的问题 | 现有条件与验收 |
|---|---|---|---|
| 1 | 新基线与 BootGuard | 更新后版本、备份和恢复点对不上 | 将当前启动 Image 哈希与 ZIP 对齐；取得当前槽位/启动状态/模块证据。BBG 默认未保护 boot/recovery，不能代替启动恢复 |
| 2 | MGLRU 开关 + ZRAM/PSI 观察 | 压力下反复回收、杀后台、切回卡顿 | ZIP 已有 MGLRU，但编译默认关闭；先读取运行 enabled。若实际关闭且补丁来源可审查，提出一次可回滚的对照试验，未确认前不写节点 |
| 3 | NoActive 解冻策略与后台预算 | 待机频繁唤醒、通知不及时、冻结依赖导致跳转卡顿 | 保留现有 ReKernel-X 后端。先确认配套接收正常和白名单，不再叠加冻结器或重复 hook；分别测通知与切回延迟 |
| 4 | VAS/uclamp/WALT 的观测与逐项调整 | 前台唤醒排队、突发升频迟滞、不必要的迁移和峰值核调用 | 运行 governor 已确认 WALT，采集其实际参数与真实 trace，再确定调整值；schedutil 虽编入，当前未使用 |

MGLRU 根据页面访问情况组织回收；它不能保证增加常驻应用数，也不能用更激进的保留时间代替 LMKD。ZRAM 用 CPU 压缩换取内存空间，单纯增加容量或换算法不能证明更快。NoActive 冻结影响“是否可运行”，调度器处理“已经可运行的任务”；两类等待必须分开统计。

## 参数应该往哪里调

以下是测量后的决策规则，不是可以直接写入手机的参数表。任何试验先保存读回值、确认实际节点语义、列出目标值和恢复方式，再请求用户授权。先临时验证，最后才考虑开机持久化；不能假定重启必然恢复，因为现有模块可能重新写参数。

| 参数 | 单位/范围/当前默认 | 何时考虑调整 | 回滚及门禁 |
|---|---|---|---|
| MGLRU enabled | 位掩码；ZIP 编译默认关闭，实机未知 | 存在回收压力、refault 或切回停顿时，比较原值与本机支持的启用组合 | 恢复捕获的原始掩码；不直接套用其它内核的 0x7 |
| MGLRU min_ttl_ms | 毫秒；实机未知 | 第一轮保持原值；过大可能加重内存不足/提前 OOM | 不预设 1000/3000 等桌面经验值 |
| ZRAM disksize / comp_algorithm | 字节/算法名；截图 16 GiB、LZ4KD | 实测压缩 CPU 成本、分配器占用、swap churn 后再比较 | 在线更换算法通常需要停用并重新初始化 swap，本轮不执行；另备维护流程 |
| vm.swappiness | 无量纲，通常 0–200；截图 100，须按本树核验 | 若压缩/换入成本导致停顿才考虑降低；若文件缓存抖动而压缩成本低可研究另一方向。不能见数值高就降 | 一次一个候选值，恢复真实读回值；不能以“剩余 RAM 更多”为唯一目标 |
| vm.watermark_scale_factor | 万分比；截图 46，即缩放值 0.46%，不代表固定预留 0.46% 总内存 | direct reclaim 与 kswapd 工作时机确有问题时才比较 | 按该 5.15 补丁树核验范围；过高会改变可用内存和回收负担 |
| uclamp min/max | 调度内部 0–1024；不同 cgroup 接口可能用百分比表示，必须区分 | 前台真实 runnable 延迟超目标且无热限频时研究短时 min 提示；后台限制须保证重要服务公平性 | 读取实际路径、单位、上下级约束；不统一锁最大，不限制系统关键线程 |
| schedutil 升/降频 rate_limit | 微秒；路径、分组与实机值未知 | 实测频率响应造成错帧，才研究减小升频延迟；频繁变频则研究滞后 | 先确认 governor 实现及厂商 Power HAL 是否覆盖；按 policy 保存/恢复，不按 CPU 类型猜 policy 数量 |
| NoActive 冻结延迟/白名单 | 秒或应用集合，取决于实际 UI/版本 | 通知、导航、音乐、相机/分享调用依赖出现问题时调整对应规则 | 保留上一份规则；不全局冻结系统服务，不同时启动第二套第三方冻结器 |
| I/O scheduler/read_ahead_kb | 算法名/KiB；实机未知 | 用混合读写尾延迟验证当前 none/mq-deadline/BFQ 等支持项 | UFS 多队列不存在普适最优值；不盲换 BFQ、不把预读拉大 |

参数来源是当前 ZIP 配置、用户截图及 Linux 对应文档。运行值优先于编译默认；Linux 最新文档中的新增接口不能直接假定回移到此 5.15 内核。

## 可以实现的新技术及成本

| 技术 | 具体用途 | 本项目可实现程度 |
|---|---|---|
| PSI 驱动的压力记录与离线分析 | 区分 CPU 等待、内存回收停顿、I/O 等待，避免把所有卡顿归因于调度器 | 可先做只读工具；PSI 已编入，不需再打补丁。分析不自动调参 |
| VAS 三策略 | Balanced 平衡响应；Performance 重视帧时间尾部；Efficiency 减少无效升频和迁移 | C 原型、配置及主机/对象测试已完成；真实 hooks、校准、ABI 与性能验证未完成，不是现成可安装模块 |
| pstore/ramoops 故障留证 | 重启后尽量保留 panic 信息，关联 BootGuard 镜像和配置 | 驱动已编入；需 DT 预留、实际记录、恢复环境验证。不保证断电或极早期故障日志 |
| BBG 设备策略审查 | 检查关键分区保护范围、合法 OTA/恢复写入与审计 | 先确认活动 LSM；若扩大 boot 保护需改源码/构建并验证更新与恢复流程，不通过试写真实分区验收 |
| NTSync | 给采用该接口的 Wine/Winlator 减少 Windows 同步对象模拟开销 | 已通过历史 5.15 驱动对象编译；仍需完整链接、上游 selftests、权限和用户态兼容。只对相应应用有意义 |
| BBRv3 + fq | 某些链路下改善 TCP 发送吞吐、排队与丢包恢复 | 需可靠的 5.15 回移源码和 ABI/网络回归；保留 Cubic 对照。不会强制下载服务器使用 BBR，也不直接加速 UDP 游戏 |
| DroidSpaces | 在 Android 内核上运行 ARM64 Linux 用户空间和容器工作负载 | 缺 SYSVIPC、PID/IPC namespace、devtmpfs 等，需配置、KABI 和 SUSFS 可见性适配；单独实验分支，成本高于调参 |
| DAMON 有限额回收 | 在适合的空闲/低压力场景研究主动回收冷内存 | 驱动已编入，先看是否启用；与 MGLRU、LMKD、NoActive 交互复杂，不建议第一轮全开 |
| WireGuard | VPN、访问自建服务或内网 | 内核已有；需要用户态和对端配置，不是新内核优化工作 |
| F2FS/fs-verity/CFI 等维护 | 文件系统可靠性、文件完整性、控制流防护 | 保留已有能力。新修复逐个核对来源及回归，不一键开启所有新配置或关闭安全检查 |

ZRAM writeback、无差别日志静默、CPU 身份伪装不列为首轮性能优化。EEVDF 保留独立研究；不做 GPU 降压/超频或 sched_ext。

## 最小对照方案

1. 固定 OS、内核、Root/NoActive/模块版本、亮度、刷新率、网络、充电状态和温度范围；先记录 baseline。USB 插线时的电量变化不作为续航提升证据。
2. 场景包括日常切回、后台通知、目标游戏帧时间、多任务内存压力和离线待机。禁止人为破坏系统测试回退。
3. 同一场景按 A/B 或 ABBA 交错测量；每轮只改一个变量，保留每次原始数据。p95/p99 必须有足够样本，不能以几次手感给出百分比。
4. 前台延迟、通知可靠性、LMKD kill/refault、PSI stall、峰值温度与耗电共同验收；出现 ANR、通知丢失、异常杀进程、热降频恶化即恢复原值。
