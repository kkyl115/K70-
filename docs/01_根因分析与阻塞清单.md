# 根因分析与阻塞清单

## 1. 历史上三次卡 Logo 的技术解释（按证据强度排序）

### R1. LKM 与 Built-in 叠加（证据最强）

- 你的 root 是 **SukiSU LKM**（`init_boot` 里带 `kernelsu.ko`，`ksud` 在 second stage 加载）。
- 一旦在管理器里执行"直接安装 / 安装到 boot"，就会把 **built-in KernelSU** 编进 kernel，同时 `init_boot` 里遗留的 LKM 逻辑仍在运行。
- 两套 root 同时接管同一启动链 → 早期 init 阶段反复重启或挂死，现象就是**卡 Logo / 闪 Logo**。
- 你描述的第 2 次（旧 GKI 能开机，SukiSU 管理器直接安装后卡 Logo）完全符合这一条。

**规则（已写入本工程纪律）**：同一设备只允许一种 root 形态。要上 built-in，必须先**用 stock init_boot 回滚 LKM**，再刷 built-in 内核；反之亦然。禁止叠加。

### R2. sub_level 与 vendor 模块 vermagic 不匹配

- 你之前用 `--sub-level 178` 是对的（当前内核 `5.15.178`）。
- `vendor_dlkm` 与 `vendor_boot` 里的模块 vermagic 咬死 `5.15.178-android13-8-…`，跳 sub_level 会触发 `Invalid module format`，早期启动即失败。
- 本次环境实测证实当前内核串是 `5.15.178-android13-8-g362d545d31a5`，**与任务书里记录的 `g6f2f96be86b9-ab13729987` 不同**，说明镜像被换过。任何"上次能开机"的结论都不能直接复用。

### R3. 构建源头选错（小米 vendor 树 vs ACK）

- 设备跑的是 **GKI `android13-5.15`**。
- `MiCode/Xiaomi_Kernel_OpenSource` 的 `bsp-vermeer-t-oss` 是 **Android 13 (`T`)** 的厂商树，其 KMI/符号表与 HyperOS 3.0.302（Android 16）上的 `android13-5.15` GKI 不对应。
- 拿 vendor 树产物当 GKI 替换镜像刷进去 = KMI 不匹配 → 卡 Logo。
- **正确路线：基于 ACK `android13-5.15`（对应 android13-5.15-2025-03 分支）+ SukiSU/SUSFS 补丁 + 与 178 对齐的 sub_level。**

### R4. boot header / AVB 状态

- `boot_a.img` 是 192 MiB（=201326592 字节），`vendor_boot_a.img` 96 MiB，`init_boot_a.img` 8 MiB。
- 刷入时必须用匹配的 `header_version`（Android 13+ GKI 常见 v4）与正确的 ramdisk 打包方式；混用 boot/init_boot 的 header 版本会直接不进 bootloader。

## 2. 构建侧硬阻塞

| 阻塞 | 事实 | 影响 |
|---|---|---|
| 主机架构 | 本机 `aarch64` | AOSP 预编译 clang-r4xx 与 Kleaf/Bazel 工具链**只有 x86_64 版**，无法在本机编译 GKI |
| 无 root | Termux 进程 `uid=10369`，无 su | 读不到 `/proc/config.gz`、`Module.symvers`、KMI 符号表、zram 算法 |
| 无法访问你的 GitHub | 不能代你登录 | Actions 的 Run workflow 必须你本人点 |
| 不刷机纪律 | 你要求且我遵守 | 真机启动验证只能你做 |

## 3. 让 Root 重新可用（三条路，按推荐度）

### 路线 A（推荐）：给 Termux 授权

1. 打开 **SukiSU Ultra 管理器**，确认首页显示"工作中 / Working"且版本 `v4.2.1-r2`。
2. 进「超级用户」→ 确认列表里有 `Termux`（包名 `com.termux`）。没有就在「应用」里手动添加并授予。
3. **完全退出** ZeroTermux（从最近任务划掉），重新打开。
4. 在 Termux 里执行：
   ```bash
   tsu -c id      # 期望: uid=0(root)
   ```

### 路线 B（最稳，不依赖 Termux 授权）：用管理器自带 root 终端

SukiSU 管理器的"终端/Shell"页面本身就以 root 运行。在本仓库里已写好脚本：

```bash
# 在 SukiSU 管理器自带的终端里执行：
sh /sdcard/Download/vermeer-ultimate-kernel/scripts/collect_evidence_root.sh
```

它把只有 root 才能拿到的证据写到 `/sdcard/Download/vermeer-ultimate-kernel/evidence/root_<时间戳>/`，之后我用文件工具直接读，不需要 Termux 有 root。

**这是当前最可执行的下一步。**

### 路线 C：只读降级（不推荐长期使用）

BootGuard 预检、备份哈希核验、CPU 拓扑这些不需要 root，已经能跑。但**内核 config、模块 CRC、KMI 符号表永远拿不到**，因此不能进内核构建阶段。

## 4. 明确不做的事

| 项 | 原因 |
|---|---|
| 自行切换启动槽位 | 你明确禁止，且 B 槽状态未知 |
| 覆盖 A 槽 | 唯一可用回滚基线 |
| 关闭 AVB / SELinux | 破坏安全模型且不解决问题 |
| 擦除 Data | 不可逆 |
| 声称"双次失败自动回退已实现" | 需 bootloader 能力验证，未验证 |
| 在本机"编译内核"并给镜像 | 物理不可能（架构不符） |
| 给你一个"提升 X%" 的 VAS 数据 | 无实测，编造即为伪证 |
