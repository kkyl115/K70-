### 对 VAS 的直接约束（这是设计的前提，不是猜的）

1. **cpu3–cpu6 只有一套频率表**，A715×2 与 A710×2 同处 policy3。任何"给 A715 单独设频"的想法在当前内核配置下**无法通过 cpufreq 实现**，只能靠 uclamp/迁移策略做差异化。而本机读不到 uclamp 接口（`/sys/devices/system/cpu/cpu*/uclamp` 未出现在输出中），需 root 后复核。
2. **policy 数量（3）≠ 核心类型数量（4）**，已按任务书要求实证。
3. 原厂用 WALT 而非 PELT 为主路径。任何替换 governor 的方案都必须先证明不劣化，不能直接改 `scaling_governor`。

## 6. init_boot 三个不同变体的哈希关系（重要发现）

| 文件 | SHA-256 | 与 A 槽关系 |
|---|---|---|
| A槽备份 `init_boot_a.img` | `e70351d2…9e7a` | 基准 |
| `kernelsu_patched_20261027_025206/030639/103008.img` | `e70351d2…9e7a` | **完全相同** |
| `init_boot.img`（Download 根目录） | `0fc9dc7c…4904` | 不同 |
| `kernelsu_patched_20261026_210859/212337.img` | `0fc9dc7c…4904` | 不同 |
| `init_boot-stock.img` | `1d384561…b41a` | 不同 |

解读（仅陈述事实与最可能解释）：
1. "patched" 产物与 A 槽镜像**字节完全一致**，说明这批 patch 输出并非新增内容，而是**复用了/复制了同一份镜像**。真正的 SukiSU-LKM 打补丁一定会改变镜像字节（要插入 `kernelsu.ko` 与修改 ramdisk），因此这批产物**不能作为"补丁已生效"的证据**。
2. 存在三份互不相同的 init_boot（`e703…`、`0fc9…`、`1d38…`），在无法读区块设备的情况下，**无法断定当前 A 槽里跑的是哪一份的语义**（备份哈希 = 线上内容，但"线上内容是不是真被 patch 过"读不到 `/data/adb` 就没法确认）。
3. 采集到的 `SukiSU_install_log_2026-10-27-04-10-40.log` 显示一次打补丁失败：
   `Bootdevice: /dev/block/by-name/boot_b` → `Patch Error: open /dev/block/by-name/boot_b → Permission denied (os error 13)`
   即**在没有 root 的进程里打补丁必然失败**，而且目标是 **boot_b**（B 槽），与"A 槽不许动"原则冲突，应永久禁用该路径。
